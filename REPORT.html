모든 배수는 원본 SimPy를 Python 3.9에서 돌린 결과 대비입니다. 측정 방식: 조합마다 새 프로세스에서 5라운드를 번갈아 실행한 중앙값. 6개 조합 모두 이벤트 순서 trace digest가 원본과 같습니다(불일치 0건).

결론

  • SimPy 내부를 고치고 핵심 6개 모듈을 Cython으로 컴파일했습니다. API와 시뮬레이션 결과는 원본과 같습니다.
  • 현재 환경(Python 3.9)에서 9개 워크로드 합계가 2.06배 빨라졌습니다. Python 3.14에서는 2.37배이고 모든 워크로드가 2배 이상입니다.
  • 라이브러리 연산 자체(사용자 코드를 거의 뺀 측정)는 Python 3.9에서 2.5~3.6배 빨라졌습니다.
  • 실제 모델에서 얼마나 빨라질지는 전체 시간 중 SimPy가 차지하는 비중에 따라 다릅니다. 사용자 코드(generator 본문, random 호출 등)는 이번 작업으로 빨라지지 않습니다.

표: 중앙값(초)과 배수

어떻게 했는가

사용자분이 제안하신 6단계를 그대로 따랐습니다. 변경은 "하나 바꾸고 → 측정하고 → 유지 또는 되돌리기"를 반복하는 방식으로 진행했습니다.

  1. 기준 성능 측정. seed를 고정한 결정적 워크로드 9개로 하네스를 만들었습니다(bench/workloads.py). 각 워크로드는 시뮬레이션 중 주요 시점을 trace로 남기고, 그 해시로 원본과 개선본의 이벤트 순서가 같은지 확인합니다. 같은 코드끼리 돌린 A/A 측정의 노이즈는 순수 Python에서 ±2%, 컴파일 트리끼리는 ±4%였습니다.
  2. 코드 전체 확인. core.py, events.py, resources/*.py를 포함해 약 2,100줄을 전부 읽었습니다.
  3. 최적화 지점 도출. 원본은 cProfile로 봤습니다. 컴파일 버전은 내부가 보이도록 CY_PROFILE=1 빌드로 봤습니다.
  4. 프로파일링. 연산별 마이크로벤치(bench/micro.py)로 어떤 연산이 덜 빨라졌는지 찾았습니다.
  5. 개선 적용. 비중이 큰 것부터 적용했습니다. 모든 변경은 회귀 게이트(bench/gate.sh)를 통과해야 남겼습니다. 게이트는 upstream 테스트 스위트, API 경계 동작 probe 29개(출력이 원본과 글자 단위로 같아야 함), 벤치마크 digest 일치를 확인합니다.
  6. 개선 후 측정. Python 3.9, 3.12, 3.14 각각에서 원본과 개선본을 한꺼번에 번갈아 측정했습니다.

정확성 검증과 발견한 버그

  • upstream 테스트 스위트: 원본과 같은 결과입니다(129개 통과, 1개 실패). 실패하는 test_exception_chaining은 원본도 Windows 경로 문제로 똑같이 실패합니다. 벽시계 시간에 의존하는 test_rt.py는 원본에서도 흔들려서 최대 3회 재시도합니다.
  • trace digest: 6개 조합 모두에서 원본과 일치합니다.
  • API 경계 동작 probe: float, numpy, Fraction 값을 priority·capacity·amount·delay로 넣거나, fail()에 예외가 아닌 값을 넣는 등 29개 경우의 출력이 원본과 글자 단위로 같습니다. numpy가 없는 3.12/3.14 venv에서는 24개입니다.

작업 중 발견하고 고친 버그

Cython은 기본적으로 함수 인자의 타입 annotation을 실제 타입 검사로 씁니다. 그래서 컴파일 버전에서 priority=1.5가 1로 잘렸고, 요청 처리 순서가 원본과 달라졌습니다. capacity=inf는 OverflowError를 냈고, fail('x')의 예외 종류도 바뀌었습니다. 벤치는 정수 priority만 썼고 기존 테스트도 이 경우를 다루지 않아서 처음에는 드러나지 않았습니다. annotation_typing=False로 annotation을 문서 용도로만 남기고 타입 지정은 전부 .pxd로 옮겨서 고쳤습니다. 같은 문제를 다시 잡도록 bench/compat.py를 게이트에 넣었습니다.

원본과 동작이 다른 점

일반적인 사용(env.process, timeout, request/put/get, with 문, interrupt, 조건 이벤트)에는 차이가 없습니다. 차이는 다음과 같은 드문 사용 방식에서만 생깁니다.

  1. Environment.schedule()을 서브클래스에서 재정의해도 내장 이벤트는 그 메서드를 거치지 않고 큐에 직접 넣습니다. env.step을 재정의하거나 패치하는 방식은 그대로 동작합니다.
  2. (컴파일 버전) 이벤트의 env는 Environment(또는 서브클래스)이거나 None이어야 합니다. Put/Get의 resource는 BaseResource 서브클래스여야 합니다. duck-typing으로 만든 가짜 객체는 TypeError가 납니다.
  3. (컴파일 버전) Put, Get, BaseResource가 더 이상 typing.Generic/ContextManager를 상속하지 않습니다. Put[X] subscript와 isinstance(req, AbstractContextManager)는 그대로 동작합니다.
  4. (컴파일 버전) _do_put/_do_get은 자기 이벤트 타입을 기대합니다. Python 서브클래스에서 재정의하는 것은 그대로 지원합니다.
  5. run() 경로의 traceback에 step 프레임이 하나 빠집니다.

연산별 비용

마이크로벤치 결과입니다. 단위는 ns/회입니다. bench/micro.py를 2번 실행해 더 작은 값을 썼고, 각 실행도 3회 반복 중 최솟값입니다. 배수는 같은 Python 버전의 원본 대비입니다.

아직 설명하지 못한 점: 개선본의 연산당 비용이 3.14에서 3.9보다 큽니다(timeout 391 → 521ns). GC를 꺼도 수치가 같아서 GC는 원인이 아닙니다. Cython이 3.14용으로 생성하는 코드 경로를 의심하지만 검증하지 않은 추정입니다. 그래도 사용자 코드가 빨라진 몫이 더 커서 end-to-end로는 3.14가 가장 빠릅니다.

  • Python 3.12/3.14용 wheel(cp312, cp314)도 dist/에 있습니다. 세 wheel 모두 깨끗한 venv에 설치해서 테스트했습니다.
  • 다시 빌드하려면 pip wheel . --no-build-isolation을 실행합니다. Cython과 MSVC(VS 2017 이상)가 필요합니다.
  • C 컴파일러가 없는 환경에서는 src/simpy를 순수 Python으로 쓸 수 있습니다. 이 경우 합계 1.20배입니다(priority_resource 3.37배).

추가로 권하는 것 (라이브러리 밖)

  1. Python 3.14로 올리기. 같은 개선본이 2.06배에서 2.37배로 올라갑니다. 3.12와 3.14 측정은 uv로 만든 격리 환경(build/venv312, build/venv314)에서 했고, 시스템 Python은 건드리지 않았습니다.
  2. GC 조정. conditions 워크로드에서 GC를 끄면 1.03초가 0.80초로 줄었습니다(약 20%, 진단용 2회 측정). dse_mix에서는 차이가 없었습니다. 모델 구성이 끝난 뒤 gc.freeze()를 호출하거나 gc.set_threshold() 값을 키워 보시길 권합니다.
  3. 사용자 코드의 random.randint 줄이기. 한 번에 542ns가 걸리는데, 이는 개선본에서 timeout 하나를 처리하는 비용(약 400ns)보다 큽니다. numpy로 난수를 미리 생성하거나 random.random() 기반으로 바꾸면 체감 속도가 더 오릅니다.

다음에 해볼 만한 것

  1. 3.14에서 늘어난 연산당 비용의 원인 찾기
  2. ConditionValue를 cdef로 전환하고 조건 이벤트 경로 정리하기(conditions가 3.9에서 1.57배로 가장 낮음)
  3. 실제 DSE 모델을 CY_PROFILE=1 빌드로 프로파일하기
